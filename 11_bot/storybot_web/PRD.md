# 스토리봇 웹서비스 요구사항 명세서

## 1. 목적과 범위

사용자가 스토리봇으로 이야기를 생성하고 게시하며, 다른 사용자가 게시한 이야기를 읽고 좋아요를 누를 수 있는 최소 기능 웹서비스를 만든다.

백엔드는 FastAPI, 프론트엔드는 React를 사용한다. 이번 작업의 산출물은 요구사항 명세서이며, 실제 서비스 구현과 배포는 별도 작업이다. 기존 코드봇 서비스와 루트의 `PRD.md`는 변경하지 않는다.

## 2. 확정 사항

| 항목 | 요구사항 |
| --- | --- |
| 명세 위치 | `storybot_web/PRD.md` |
| 모델 | `storybot/model_pretrain.pt` |
| 생성 방식 | 사용자가 이야기의 시작 부분을 입력하면 뒷부분 이어쓰기 |
| 생성 입력 한도 | 자체 토크나이저 기준 최대 128토큰 |
| 추가 생성 한도 | 최대 128토큰 |
| 게시 흐름 | 생성 결과 확인 → 제목 입력 및 본문 수정 → 게시 |
| 생성 기록 | 미게시 결과를 포함해 본인의 생성 기록 조회 |
| 공개 범위 | 공개 게시물은 다른 회원과 비회원 모두 목록·본문 조회 가능 |
| 수정·삭제 | 해당 스토리 작성자만 가능 |
| 회원가입 | 아이디·비밀번호·닉네임 |
| 회원정보 수정 | 본인의 닉네임·비밀번호 변경 |
| 로그인 유지 | 브라우저를 닫았다 열어도 로그인 시점부터 7일간 유지 |
| 로그아웃 | 로그인 상태 즉시 해제 |
| 좋아요 | 로그인한 회원당 게시물별 1개, 다시 누르면 취소, 본인 게시물에도 가능 |
| 목록 | 최신순, 페이지당 10개 |
| 저장소 | SQLite |

사용자는 추천 구성에 동의했으며, 다른 사람의 게시물을 조회할 수 있어야 하고 수정·삭제는 할 수 없어야 한다고 추가 확인했다.

## 3. 참조 소스와 분석 근거

참조 범위는 아래 두 위치로 한정한다.

- `C:\Users\KDS-30\Desktop\class\11_bot\storybot`
- `C:\Users\KDS-30\Desktop\class\11_bot\04.ipynb`

| 소스 | 확인된 내용 | 반영 사항 |
| --- | --- | --- |
| `04.ipynb` 사전학습 설정 | `context_len = 256`, 어휘 크기 10000 | 문맥 길이 256을 기준으로 입력·생성 예산 설정 |
| `04.ipynb` 추론 예시 | `model_pretrain.pt`, `temperature=1.0`, 예시별 생성 길이는 150·200·300 등 | 모델은 확정한 사전학습 모델 사용, 생성 길이는 확정값 128을 명시 |
| `storybot/model.py` | 체크포인트에서 모델 설정을 로드하고 생성 중 KV 캐시 사용 | 실제 로드 시 문맥 길이를 확인하고 요청 간 캐시 혼합 방지 |
| `storybot/utils.py` | `generate()` 기본 추가 생성 길이는 1000, 시작 시 `clear_cache()` 호출 | 웹서비스에서는 `max_new_tokens=128`을 명시 |
| `storybot/utils.py` | 입력과 생성 내용을 함께 반환하며 종료 토큰은 제거 | 전체 이야기 결과 표시, 입력을 다시 중복 연결하지 않음 |
| `storybot/tokenizer.py` 및 `merge_rules.pkl` | 자체 BPE 토크나이저 | 실제 토큰 수로 입력 한도 검증 |
| `04.ipynb`, `tiny_stories_dpo.json` | 영어 이야기와 행복한 결말 선호 학습 예시 | 한국어 생성 품질이나 번역 기능을 보장하지 않음 |

`generate()`는 `ids`를 잘라도 실제 추론에는 `next_id`와 누적 KV 캐시를 사용한다. 코드봇과 같은 최근 256토큰 문맥 이동 방식이라고 가정하지 않는다. 현재 명세는 입력 128토큰과 추가 생성 128토큰의 합계를 256 이내로 제한한다.

체크포인트 로드·실제 추론은 이번 문서 작성 과정에서 실행하지 않았다. 구현 시 `model.max_context_len`이 예상값 256과 다른 경우 사용자에게 확인한다. 노트북의 외부 모델 평가 호출은 웹서비스 범위에 포함하지 않는다.

## 4. 화면과 사용자 흐름

### 4.1 메인페이지

- 공개 게시물을 최신순으로 표시한다. 각 항목에서 제목·작성자·게시일·좋아요 수를 확인하고 본문을 열 수 있다.
- 목록은 페이지당 10개씩 조회하며 이전·다음 페이지로 이동할 수 있다.
- 비로그인 상태에서는 회원가입·로그인으로 진입할 수 있다.
- 로그인 상태에서는 로그아웃·회원정보 수정·스토리 생성·내 생성 기록으로 진입할 수 있다.
- 로그인 상태에 맞는 메뉴를 표시하고 새로고침 후에도 로그인 유지 여부를 반영한다.

### 4.2 스토리 생성 및 게시

1. 로그인한 사용자가 이야기의 시작 부분을 입력한다.
2. 생성 버튼을 누르면 서버가 입력과 로그인 상태를 검증한다.
3. 스토리봇이 추가 내용을 생성한다. 생성 중 상태를 표시하고 같은 화면의 중복 제출을 막는다.
4. 성공한 전체 생성 결과를 본인의 생성 기록으로 저장하고 화면에 표시한다.
5. 사용자는 결과를 확인하고 게시할 제목과 본문을 편집한다.
6. 게시 버튼을 누르면 작성자를 현재 로그인 사용자로 지정해 공개 게시물을 저장한다.
7. 공개된 게시물은 다른 회원과 비회원도 조회할 수 있다.

게시 버튼을 누르기 전까지 생성 결과를 다른 사용자에게 공개하지 않는다. 빈 결과나 생성 실패를 정상 생성 기록 또는 공개 게시물로 저장하지 않는다.

### 4.3 내 생성 기록

- 로그인한 본인의 성공한 생성 기록을 최신순, 페이지당 10개씩 조회한다.
- 기록에서 입력 내용·생성 결과·생성 시각을 확인할 수 있다.
- 게시하지 않은 결과도 기록에 남으며 서버 재시작 후에도 유지된다.
- 다른 사람의 생성 기록은 조회할 수 없다. 다른 사람에게 공개되는 것은 별도로 게시한 스토리다.
- 생성 기록은 생성 당시의 결과를 보관한다. 게시물의 편집 대상 본문과 구분하며, 기록 편집·삭제를 별도 기능으로 추가하지 않는다.

### 4.4 게시물 조회·수정·삭제

- 모든 방문자는 공개 게시물의 제목·본문·작성자·게시일·좋아요 수를 볼 수 있다.
- 작성자 본인에게만 수정·삭제 버튼을 표시한다.
- 수정은 본인이 작성한 게시물의 제목과 본문에 한정한다.
- 삭제한 게시물은 공개 목록과 본문 조회에서 더 이상 노출되지 않는다.
- 버튼 표시뿐 아니라 서버에서도 로그인 사용자와 저장된 작성자가 같은지 검사한다.
- 다른 사람이 게시물 ID나 요청 데이터를 조작해도 수정·삭제할 수 없다.

## 5. 회원 및 로그인 요구사항

- 회원가입 시 아이디·비밀번호·닉네임을 입력받는다. 필수값 누락과 중복 아이디는 안내하고 가입을 거절한다.
- 비밀번호 원문을 저장하거나 응답하지 않는다. 비밀번호 검증용 해시를 저장한다.
- 올바른 아이디·비밀번호로 로그인할 수 있으며 실패 시 오류를 안내한다.
- 로그인 상태는 로그인 시점부터 7일간 유지하며, 새로고침과 브라우저 재실행 후에도 만료 전에는 유지한다.
- 로그아웃 시 해당 로그인 상태를 서버에서도 무효화한다. 만료되거나 로그아웃한 인증 정보로 보호된 기능을 사용할 수 없다.
- 본인만 자신의 닉네임·비밀번호를 변경할 수 있다. 아이디 변경은 포함하지 않는다.
- 인증 상태와 작성자 정보는 서버에서 결정한다. 클라이언트가 보낸 사용자 ID만으로 권한을 인정하지 않는다.
- 비회원의 생성·게시·회원정보 변경·좋아요 요청은 서버에서 거절하고 로그인 필요를 안내한다.
- 세션/토큰 방식, 쿠키 설정, 비밀번호 세부 규칙 및 변경 시 재인증·기존 로그인 처리 방식은 구현 전에 확인한다.

## 6. 스토리봇 입력·생성 요구사항

- `storybot/merge_rules.pkl`로 로드한 `BPETokenizer`로 `len(tokenizer.encode(prompt))`를 계산한다.
- 내용이 없는 입력과 128토큰을 초과한 입력은 추론 전에 거절한다.
- 초과 시 실제 토큰 수와 최대 허용값 128을 안내한다. 입력을 자동으로 자르지 않는다.
- 글자 수·바이트 수를 토큰 수로 대신 사용하지 않는다.
- 앞뒤 공백과 줄바꿈을 임의로 제거하지 않고 실제 입력을 모델에 전달한다.
- 사용자의 시작 문장을 프롬프트로 사용한다. 지시문 템플릿이나 번역 단계를 추가하지 않는다.
- `model_pretrain.pt`와 토크나이저를 서버 초기화 시 준비하여 요청마다 다시 로드하지 않는다.
- 기존 `generate()`의 추론 모드와 기울기 비활성화를 유지하고, `max_new_tokens=128`, `temperature=1.0`으로 호출한다.
- 종료 토큰이 나오면 최대 길이 이전에도 종료한다. 반환된 전체 이야기에 입력을 다시 덧붙이지 않는다.
- 생성 캐시가 요청 간 섞이지 않도록 한다. 구체적인 동시 요청 처리 정책은 구현 전에 확인한다.
- 오류 발생 시 입력을 유지하고 실패 사유를 안내해 재시도할 수 있게 한다.
- 128토큰 입력 한도는 모델에 보내는 생성 프롬프트의 한도다. 게시물 제목·수정 본문의 저장 한도로 그대로 적용하지 않는다.

## 7. 좋아요 요구사항

- 로그인 사용자가 공개 게시물의 좋아요 버튼을 누르면 좋아요 1개를 등록한다.
- 이미 좋아요를 누른 사용자가 같은 버튼을 다시 누르면 취소한다. 빠른 더블클릭 제스처를 요구하지 않는다.
- 화면에 전체 좋아요 수와 현재 사용자의 좋아요 여부를 표시한다.
- 회원 1명은 게시물 1개에 좋아요를 최대 1개만 가질 수 있다. 저장소에서도 중복을 방지한다.
- 본인이 작성한 게시물에도 좋아요를 누를 수 있다.
- 비회원은 좋아요 수를 조회할 수 있으나 등록·취소하려면 로그인해야 한다.
- 좋아요 요청의 사용자는 서버에서 확인하며, 다른 사용자의 좋아요를 대신 취소할 수 없다.
- 새로고침 후에도 저장된 좋아요 수와 상태를 유지한다.

## 9. 최소 저장 데이터

SQLite에 아래 데이터를 영속적으로 저장한다. 상세 테이블·API 설계는 구현 전에 확인한다.

| 데이터 | 필수 내용 |
| --- | --- |
| 회원 | 내부 식별자, 로그인 아이디, 비밀번호 해시, 닉네임 |
| 생성 기록 | 식별자, 생성 요청자, 입력 내용, 전체 생성 결과, 생성 시각 |

| 좋아요 | 게시물과 회원의 연결, 동일 조합 중복 방지 |
| 인증 상태 | 선택할 인증 방식에 따른 만료·로그아웃 처리에 필요한 정보 |

공개 게시물 응답에 비밀번호 정보·로그인 인증 정보·타인의 비공개 생성 기록을 포함하지 않는다. 제목과 본문은 실행 가능한 HTML이 아닌 텍스트로 표시하고 줄바꿈을 유지한다.

| 7 | 생성 종료 | 최대 128회 추가 생성, 종료 토큰 발생 시 조기 종료 |
| 8 | 생성 기록 | 미게시 결과도 본인 기록에서 조회 가능, 다른 회원·비회원 접근 거절 |
| 9 | 게시 | 생성 결과 확인·편집 후 게시하면 공개 목록과 본문에서 조회 가능 |
| 10 | 타인 스토리 열람 | 회원 A의 게시물을 회원 B와 비회원이 모두 읽을 수 있음 |
| 11 | 수정·삭제 권한 | 회원 A만 자신의 게시물을 변경 가능; B의 직접 API 요청도 거절 |
| 12 | 좋아요 토글 | 첫 클릭 후 1개 증가, 다시 클릭하면 취소, 중복 저장 없음 |
| 13 | 좋아요 권한 | 비회원 등록 거절, 다른 회원의 좋아요 취소 불가 |
| 14 | 페이지 분리 | 11개 이상일 때 페이지당 최대 10개, 다른 페이지의 항목 조회 가능 |
| 15 | 영속성 | 서버 재시작 후 회원·기록·게시물·좋아요 유지 |
| 16 | 오류 처리 | 생성·저장 실패를 성공으로 표시하지 않고 입력과 오류 안내 유지 |

권한 검증에는 서로 다른 회원 2명과 비회원 상태를 사용한다. React 화면에서 FastAPI를 통해 실제 스토리 생성 및 게시, 다른 사용자 조회까지 이어지는 흐름을 최소 1회 검증한다. 문학적 품질·한국어 품질·특정 응답 시간은 확정된 완료 기준이 아니다.

## 11. 제외 범위

- 댓글, 답글, 팔로우, 알림, 메시지
- 검색, 태그, 카테고리, 인기순 정렬
- 이미지·파일 업로드, 외부 공유, 다운로드
- 소셜 로그인, 이메일 인증, 비밀번호 찾기, 회원 탈퇴
- 관리자 화면, 별도 신고·운영 기능
- 생성 설정 화면, 모델 선택, 재학습, 외부 AI 평가·번역
- 게시물 수정 이력, 자동 저장, 생성 기록 별도 편집·삭제 기능
- 결제, 통계 등 요청하지 않은 부가 기능

## 12. 추가 결정 원칙

구현 전 인증의 상세 방식, 가입 입력값의 세부 제한, 게시물 제목·본문 길이, 생성 기록과 게시물 연결·재게시·삭제 후 기록 처리, 상세 API 규격, 동시 요청 정책, 배포 환경을 사용자에게 확인한다. 미확정 사항을 임의로 확정하거나 새로운 기능을 추가하지 않는다.

타인의 공개 게시물 열람 허용과 작성자만 수정·삭제 가능하다는 권한 원칙은 구현 방식과 관계없이 유지한다.
